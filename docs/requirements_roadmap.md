# 有価証券報告書APIプロジェクト：完成形要件・不足要件・ロードマップ

## 完成形の要件（ゴール）
- EDINETから各企業の有価証券報告書を自動収集できる
- 収集データを項目（カテゴリ）単位で抽出・保存できる
- API経由でカテゴリ→内容を取得できる
- 取得キーはEDINETコード（将来的拡張は任意）
- バッチ処理で継続的に最新データを更新できる

## 不足している機能要件（現状との差分）
- EDINET APIからの自動収集（現在はローカルCSV読み取りのみ）
- 取得後の永続化（DB/ストレージ）
- カテゴリ単位取得API
- バッチ／定期実行の仕組み

## ロードマップ（モック/オンメモリで段階的に動作プロダクト化）

### フェーズ1: ローカルCSV API（単一ファイル固定）
- 目的: 1社のカテゴリ情報をAPIで返せる
- 実装: 固定CSVパス読み取り、`ExtractedReport`をJSON返却
- 不足機能の扱い: EDINET取得・永続化なし
- 成果物: `GET /companies/{edinet_code}/categories` が動作

### フェーズ2: EDINETコード対応（ローカルCSVルックアップ）
- 目的: EDINETコード指定で複数企業に対応
- 実装: `edinet_code`→CSVパス解決（ディレクトリ or 命名規則）
- 不足機能の扱い: CSVはローカル手動配置
- 成果物: EDINETコードでAPIが動作、未存在時は404

### フェーズ3: カテゴリ単位取得API
- 目的: カテゴリ指定で必要情報だけ返せる
- 実装: `GET /companies/{edinet_code}/categories/{category}`
- 不足機能の扱い: フィルタはオンメモリ
- 成果物: 必要カテゴリの即時取得が可能

### フェーズ4: EDINET取得の導入（オンデマンド）
- 目的: EDINETから自動取得してAPIで返す
- 実装: リクエスト時にEDINET取得→解析→返却
- 不足機能の扱い: 永続化なし、毎回取得
- 成果物: CSV配置なしで動作

### フェーズ5: 永続化の導入（最小DB）
- 目的: 取得済みデータの再利用
- 実装: SQLite or JSONストレージ
- 不足機能の扱い: 検索は不要
- 成果物: 取得→保存→再利用が可能

### フェーズ6: バッチ化（定期収集）
- 目的: 自動更新で最新データを保持
- 実装: cron/ジョブで定期取得、差分更新
- 不足機能の扱い: 失敗時はログのみ
- 成果物: 収集基盤の自動化
